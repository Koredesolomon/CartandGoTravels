# Consular AI review

## Model, passes and limits

`ANTHROPIC_API_KEY` and a model that supports Anthropic JSON structured outputs in `ANTHROPIC_MODEL` (default `claude-sonnet-5-5`). On `claude-sonnet-5-5` requests use `thinking: {type: "between_tools"}` (no extended thinking, matching the output budgets below) and server-side refusal fallback; these fields are omitted for any other configured model. Each pre-assessment normally makes two AI calls: document review/proofreading, then a compact independent audit against the same full source material. Invalid report structure gets one bounded repair attempt. Unverifiable evidence is recovered where possible, then flagged per affected item; other independently checked observations can still appear in a partial report. Model/provider failures, incomplete responses and persistently malformed structure return an error without a keyword fallback or fabricated score. Corrections changing detected numeric/date/currency facts, names, negations, commitments, protected legal terms or reading annotations are withheld; these conservative checks are not a semantic or legal guarantee. Reports include separate proposed additions and item-level verification issues. Exact evidence and correction originals come from server-owned source passages, not AI-generated quotations. Unverified items withhold readiness; potentially dependent summary claims, criterion conclusions and free-form action lists are also withheld. This does not establish document authenticity or guarantee correct AI reasoning. Scoring measures weighted supplied-evidence coverage, not approval likelihood; it is also withheld for unresolved risks, unassessable criteria, unrelated/uncertain documents, unchecked OCR or unverified official guidance. Current official pages are fetched without applicant data for Canada, the UK and the US; other destinations receive limited text/evidence review. Sources are not a complete local visa-office checklist. Allow outbound HTTPS to `api.anthropic.com`, `www.canada.ca`, `www.gov.uk` and `travel.state.gov`, and assessment route execution up to 600 seconds (240 seconds per AI pass, with a 550-second overall deadline). Each review, compact audit and optional structural-repair stage can retry a truncated response once with a larger output allowance, within the same overall deadline. Full-report stages use 7000 then 14000 output tokens; the compact audit uses 2500 then 5000. Failed reports return distinct `review_incomplete`, `report_validation_failed` or `review_failed` codes and a request reference matching the server log, without logging applicant text. Timeouts return `504 review_timeout` while keeping uploaded text available for retry. Synthetic/API regression coverage is in `tests/consular-review.test.cjs`; mocked tests verify behavior, not visa-review accuracy. With the local app running, `npm run evaluate:consular` submits only the synthetic fixture in `tests/fixtures/consular/conflicting-evidence.json` and checks salary/date contradictions, grammar, missing financial evidence and exact quotations. When payment is enabled, set `CONSULAR_EVAL_ACCESS_TOKEN` to the `ai_consular_access` cookie value from a valid paid session. To validate an existing saved report without provider calls, use `npm run evaluate:consular -- --report <path>`. This optional live evaluation normally makes two provider calls (up to six generation attempts with structural repair and stage-specific output-limit recovery, plus one retry per attempt for transient provider failures) and incurs normal AI usage costs; it is one regression case, not a calibrated accuracy benchmark.

## Document selection and reading

Pre-assessment starts with document selection. Selecting PDF, DOCX or TXT files validates only file metadata and keeps them in page memory; no text is read and no OCR or review request is sent until the user clicks **Proofread**. After that click, readable text is processed internally; PDFs containing images use the session-scoped `/api/document-ocr` endpoint. Every physical page must be accounted for. Truly unreadable document pages and truncated responses are rejected; pages containing only a signature in a signing area receive an explicit unverified-signature annotation instead of blocking readable document pages. Legible handwriting is transcribed, unclear fields remain marked, and signature/handwriting reading notes reach both review passes and appear in report limitations. Signature marks are not authenticated or used to infer a signer; reading annotations are excluded from proofreading corrections. AI-read scans receive a limited report without a readiness score because transcription has not been independently confirmed. The page shows filenames followed by the assessment results, with no extracted-text preview or confirmation step. Paste text remains an alternative. Limits remain six files, 10MB each, 30MB total, 100 pages per PDF and 60,000 characters total. Files and text stay in page memory and are not saved by these routes. Replacing input or switching input mode cancels pending processing and ignores stale results. CV and cover-letter uploads still use browser text extraction with their 12,000-character limit. `predev` and `prebuild` copy the PDF worker and font/CMap/WASM assets from the installed PDF.js package; deploy these public assets with the app. The worker is served at `/pdf.worker.min.js` with a JavaScript content type for module-worker compatibility.

PDF reading detects ordinary, grouped and repeated image operators, including image masks. Textless pages containing visible paths (such as outlined lettering in flattened deeds) also trigger full-document OCR instead of being treated as blank. Genuinely blank pages do not trigger OCR by themselves. All uploaded documents and physical pages still need to be accounted for; the fallback does not accept missing pages or authenticate deed wording or signatures.

## Review and audit safeguards

Review and audit instructions distinguish unverified consent/registration from a claim that those events have not occurred, and require qualified legal interpretations. Addition checks withhold detected unsourced claims of completed bookings, approvals or supplied records. A name/date placeholder does not qualify an assertion that the event already happened; unknown events need a whole-assertion placeholder. Existing exact source statements and draft legal obligations remain subject to the other checks. The compact auditor receives the same backend-owned legal warnings displayed on each affected correction/addition; a warning does not make unsafe legal or factual changes acceptable. The audit receives exact backend-sourced originals and the displayed warnings beside each proposal, with original array positions preserved even when other entries were withheld. These conservative safeguards do not establish semantic accuracy or document authenticity. OCR and review requests retry a transient provider 500/502/503/504/529 once, after a one-second abortable pause, without resetting the existing provider deadline. Credential, request and usage-limit errors are not retried. Provider diagnostics record numeric status, a fixed failure category and request reference, not provider messages or document contents. Insufficient API credits return `503 provider_credit_exhausted` with a service-unavailability message instead of advising a different PDF or model.

## Proofreading and suggested additions

Proofreading uses a separate `proofreadingCatalogue` of paragraphs up to 4000 characters; assessment evidence retains its 400-character passage catalogue. The AI selects `documentId` and `excerptId`; the backend retrieves the exact original wording. Suggested replacements may use new wording, up to 8000 characters, subject to factual, commitment, legal-term and annotation checks. They do not need to occur in the source. Legal-document changes are explicitly drafts requiring review by the parties and a qualified legal reviewer. `suggestedAdditions` contains up to eight separate proposed new passages, with a placement and rationale but no invented `Original` or source quotation. Unknown facts must use placeholders; detected invented names, numbers or authenticity/ownership declarations and changes to issuer-controlled records are withheld.

## Source recovery and partial reviews

Source recovery permits unique ID-format differences and exact wording with whitespace/Unicode formatting differences, returning the actual original characters. It never guesses changed words, numbers or a different document. Older literal originals and passage IDs remain supported under source checks. An unrecoverable source reference flags its affected criterion, finding, correction or addition in `verificationIssues`; other checked observations remain available. The backend derives each issue's `impact` from its section and document dependencies, never from an AI description of severity. Wording-only correction/addition failures produce `reviewStatus=wording_partial`: the writing criterion and readiness score remain incomplete, while the other checked evidence assessments are retained. Existing risk findings stay prominent in the status. Evidence or classification failures produce `evidence_partial`, withholding aggregate criterion conclusions and overall readiness while retaining checked quotations and unrelated observations. Section-wide concerns, including omitted risks in empty sections, and concerns about overall summary/actions produce `broader_review_required`. These require broader human review before reliance. For every partial review, free-form summary/action lists are replaced with scoped backend wording because their item dependencies are not tracked.

## Compact audit

The compact auditor reports concerns against indices in the original draft, before failed source entries are removed. Questioned document classifications become uncertain; their dependent criteria, findings, corrections and suggested additions are withheld. Detailed audit reasons and withheld-item labels remain transient internal diagnostics and are excluded from public API/background results. Public `verificationIssues` contain only allowlisted metadata and a short, fixed explanation for their category; the UI also uses these fixed explanations when rendering older results. Detailed reasons are not written to application logs. Malformed audit output or invalid item indices cannot become approved reports. Malformed categories, missing document/criterion coverage and oversized lists still fail the whole report. An unchanged `[unclear]` or signature annotation can remain alongside a grammar correction, but changing an annotation or correcting an annotation alone is withheld.
