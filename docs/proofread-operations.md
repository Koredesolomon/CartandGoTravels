# Proofread background jobs and troubleshooting

## Background processing

Proofread uses background processing for both scanned-PDF reading and the subsequent AI review. The browser requests `Prefer: respond-async`; each validated upload/review returns `202` and an opaque job reference before any provider call. Next.js `after()` runs the work while the browser makes short, private/no-store requests to `/api/consular-jobs/[id]`. Every poll and cancellation requires the originating browser session; with payment enabled, this must also be the same unexpired paid session that started the job. Polls do not contain documents or make provider calls. Input changes and page exit cancel the browser request and attempt to abort its job; completed jobs are deleted after the client receives their result. Uncollected results expire automatically after 60 seconds, and job deadlines abort pending work. Original uploads, text and results remain only in process memory and are never written to disk or MySQL. Concurrency is bounded to four active jobs per process and two per browser session. This workflow requires a persistent Node.js process running `next start`; multi-instance deployments must route a session's job requests to the same process. A restart loses unfinished jobs and returns a retry message. Hosting must allow background execution for the existing 300-second OCR and 600-second review route limits, but HTTP connections no longer wait for the AI passes. Requests without the async preference retain the synchronous API behavior for existing integrations and local evaluation.

## Diagnosing production Proofread failures

Production Proofread failures: the OCR upload and review clients handle HTML/empty responses from hosting proxies without displaying JSON parser errors or proxy content. Unpaid/expired-session responses still lock the tools even if their body is HTML. Other unexpected responses show the failing endpoint and HTTP status; timeouts retain the selected inputs for retry. For immediate failures, inspect the failing POST in the browser Network panel and the hosting logs: `403` indicates a blocked request, `413` an upload-body limit, and `404`/`405` an unavailable route or method. Ensure `/api/document-ocr` reaches the current Node.js deployment, the hosting upload limit permits the supported 10 MB PDFs, and the Node.js process permits the background execution limits below. Rebuild and restart after deploying code changes. A clearer client error does not change a hosting restriction.
